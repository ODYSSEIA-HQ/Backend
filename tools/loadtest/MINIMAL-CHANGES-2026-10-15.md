# 2026-10-15 小改动优化验证

## 范围

沿用 NodeBB + Centrifugo 和现有 API、数据结构、插件 hook。本轮没有实现新的作品实体或嵌套论坛，也没有修改 Fluxer。工作区中此前的改动全部保留。

生产代码的主要性能改动仅在 `src/api/chats.js` 的内部限速函数：

1. 两种冷却时间均已过，直接更新会话发送时间并放行。
2. 两种冷却时间相同，不查询声望和管理身份。
3. 需要区分身份时，先读声望；声望不足才调用 `isPrivileged`。

`isPrivileged → getModeratedCids` 会遍历全部分类以检查管理权限。此次省去的是不影响限速结果的调用，没有新增权限缓存、降低限速、取消房间授权，或改写用户权限模型。创建聊天室也共用该函数。

该函数没有替换 hook；使用 14 行新增、7 行删除的局部 vendor patch，避免运行时替换 NodeBB 方法。README、Dockerfile 和 Compose 已登记补丁，升级上游时运行回归测试。

## 缓存与兼容修复

- 分类后台刷新必须同时具备回环连接地址和本 worker 随机凭证。外部伪造 `x-odysseia-cache-refresh: 1` 不再跳过缓存和插件限频。
- `ODYSSEIA_CATEGORY_CACHE_TTL_MS=0` 现在确实关闭缓存；stale 时长设为 0 也会生效。
- 缓存满时更新已有分类，不再误淘汰一个无关分类。
- 分类路径匹配补上边界，不缓存 `/api/category/123oops`。
- Compose 现在实际传递 `ODYSSEIA_DISABLE_NATIVE_CHAT_NOTIFY`。值为 0 时恢复 NodeBB 原生通知链；默认仍为原来的 1，启用原生链后的容量需要另测。
- 修复现有冒烟脚本的重复 BOM，以及查询不存在的测试账号时读取空对象的问题。

## 验证方法

`node --test tools/tests/hot-paths.test.cjs`：8 项测试通过。其中限速矩阵覆盖 640 组条件，比较原限速公式和实际聊天 API 的判断；另测新会话首次发送、同会话再次发送、管理身份撤销、房间拒绝访问、原生通知开关、刷新凭证及缓存更新。

最终镜像完成负载测试后，现有业务冒烟再次通过 20/20（登录、发帖、搜索索引、slowmode、删除/恢复权限、广播凭证）；BOM 和空对象错误不再出现。插件 TypeScript 检查、JavaScript 语法检查、Compose 配置检查和 `git diff --check` 均通过。运行容器源码 SHA-256 与工作区一致，12 个 worker 探活均为 200。

沿用已有负载：3000 分类、约 30000 讨论主题、4000 房间、60 个账号，每秒 100 次聊天写入、30 次匿名分类读取。短测目标 500 WS，ramp 20 秒、hold 60 秒；完整规格目标 2500 WS，ramp 120 秒、hold 300 秒。各轮前运行相同预热。

首次只做声望短路的短测为 `minimal-after`：聊天 P95 214 ms，高于优化前的 157.85 ms，没有证明收益。实际测试用户声望均为 0，仍走完整身份检查。最终补丁加入“两种冷却均结束”的判断，单独记录 `minimal-final`，不覆盖中间结果。

## 短测结果

短测结果（500 在线目标，100 msg/s，30 read/s）：

| 轮次 | 聊天 P95 | 聊天中位数 | 分类读取 P95 | 发送成功/尝试 | 发送失败率 |
|---|---:|---:|---:|---:|---:|
| minimal-before（改动前） | 157.85 ms | 52 ms | 25.16 ms | 5997/6001 | 0.0667% |
| minimal-after（仅声望短路） | 214 ms | 49 ms | 27.43 ms | 5992/6001 | 0.1500% |
| minimal-final（最终补丁） | 49.30 ms | 27 ms | 18.62 ms | 5997/6001 | 0.0667% |

最终短测聊天 P95 较本轮基线下降约 68.8%。这是当前负载下的实测差异，不是对所有用户和硬件的承诺。最终短测预热阶段有 11 个 dropped iterations，正式短测无 dropped；预热 HTTP 错误为 0。短测采样无 swap、无 OOM。

独立 URL 的在线缓存探针记录在 `results/minimal-cache-probe.jsonl`：首次生成 2423 ms、命中 5 ms；TTL 过期后依次为 `hit-stale`（118/286/553 ms）→ `hit-fresh`（4 ms），证明本机刷新凭证在实际 worker 中有效。过期探针与完整规格负载同时进行，不能将探针延迟当作总体 P95。

## 首次完整规格结果

`minimal-full` 没有通过聊天 P95 < 500 ms 的门槛：聊天 P95 **585 ms**，中位数 35 ms，分类读取 P95 50.41 ms。29962 次发送中成功 29921 次、失败 41 次（0.1368%，诊断日志为 HTTP 403）；43 次 dropped iterations、6 次订阅拒绝。不能以短测的 49.3 ms 代替这次未达标的完整结果。

资源采样 22 次：NodeBB Docker memory usage 峰值 3.618 GiB，swap 从 0 增至 90.24 MiB，无 OOM。负载开始时 NodeBB CPU 曾超过 1100%，VM 内存 pressure some avg10 最高 1.18。以上数据表明存在资源抖动，但不足以证明 585 ms 完全由换页导致。

## 进一步诊断

只读审计种子数据的 8000 条预期成员关系，发现 3 条与数据库不一致：uid 21 / room 4、uid 20 / room 5、uid 19 / room 2。结果保存在 `results/minimal-membership-audit.json`。对三对账号/房间执行只读 HTTP 访问均返回 403（`minimal-membership-http.json`）。这解释了至少部分权限拒绝；未通过放宽真实房间权限来消除测试错误，复测保留原数据。

同一最终版本的复测采集了最大 RSS worker（PID 89）的 45 秒 CPU/GC 窗口：GC 共 195 次、累计 329.51 ms、单次最大 24.14 ms；事件循环 P99 24.02 ms、最大 60.03 ms。该窗口未观察到秒级 GC 停顿，分类权限扫描不再处于热点前列。不能由单 worker 的短窗口推断整轮没有尾延迟问题；采样本身也有开销。诊断结束已确认 inspector 关闭。

## 同版本完整规格复测

`minimal-repeat` 保持最终代码、配置和种子数据不变，重新预热后运行相同完整规格，三项门槛全部通过：

| 指标 | 首轮 minimal-full | 复测 minimal-repeat |
|---|---:|---:|
| 聊天端到端 P95 | 585 ms（未达标） | 52 ms |
| 聊天中位数 | 35 ms | 28 ms |
| 分类读取 P95 | 50.41 ms | 6.05 ms |
| 发送成功/尝试 | 29921/29962 | 29962/30001 |
| 发送失败率 | 0.1368% | 0.1300% |
| 丢弃迭代 | 43 | 0 |
| 订阅拒绝 | 6 | 5 |
| WS 错误 | 0 | 1 |

复测成功发送约 99.87 条/秒（29962 ÷ 300 秒 hold），收到 18650 个延迟样本。资源采样 21 次：NodeBB memory usage 峰值 3.561 GiB，无 OOM，VM memory pressure some avg10 均为 0；swap 保留前轮约 93 MiB，采样期间未增长。

两次完整规格的差异说明运行状态会显著影响尾延迟。复测没有重启进程，V8、数据库和系统缓存更热，也包含 45 秒 profiler。当前证据支持保留这个减少无用查询的小补丁，**不支持宣称生产环境已稳定达到 52 ms**，也没有证明首轮抖动已被根治。

下一轮验证应先让压测读取实际房间成员关系，区分合法发送负载与越权负例，再独立覆盖重启、冷缓存和原生通知启用场景；不用更长的权限缓存掩盖问题。

## 结果适用边界

- 这些是先后顺序的本机测量，非隔离随机实验。重建会清空 worker 缓存，数据库和操作系统缓存没有逐轮清空。
- Bearer 压测不带会话 cookie，原有会话限速本就不会跨请求累积。最终优化在此路径很容易命中；不能把收益比例照搬到登录浏览器频繁发送的新用户。已有测试明确验证持久会话仍然限速。
- HTTP 走内部 Caddy，WS 直连 Centrifugo；60 账号复用成大量连接，房间通常两人，未验证 2500 个独立用户或热门房间大规模广播。
- 原生聊天通知处于禁用模式。恢复 Socket.IO、站内通知、邮件后需要单独测试，不能称本结果为全功能容量。
- 分类响应缓存原有的权限变更失效机制仍待完善；本轮加固刷新入口不等于解决了所有授权缓存问题。TTL=0 可用于需要即时失效而尚未验证缓存一致性的部署。
- 失败诊断已捕捉到少量 HTTP 403；必须保留失败率，不把拒绝请求从测试分母中删掉。没有与 Fluxer 做同环境、同语义对测。
