# 2026-10-15 性能续跑报告

最终配置（分类 URI 亲和 + 每 worker old-space 384MiB/semi-space 8MiB）在本机
2500 WS 目标、100 msg/s、30 read/s、hold 300s 的完整测试中，通过既定三项门槛：
聊天 P95 133ms、分类读取 P95 27.13ms、发送失败率 0.117%。仍有残余失败，详见下文。

## 修复与证据

Caddy 的分类 API 从 round_robin 改为 uri_hash，其他 NodeBB 路径保留轮询。
公网入口与内网 :8090 共用 nodebb_cluster，避免两处配置漂移。

原先分类响应缓存位于每个 NodeBB worker 的 Map 中，轮询却让同一个分类在
12 个 worker 上分别冷加载。3000 分类、21 次/秒随机卡分类读取时，全站平均
重访约 143 秒，但单 worker 平均重访约 1714 秒，超过 TTL 300 秒及 stale
600 秒的总窗口。一次全量预热也不能热满 12 份缓存。

URI 亲和让同一 URL 的请求命中同一 worker；缓存仍按凭证和完整 URL 隔离，
权限逻辑未改。验证新父分类 URL：第一次 1807ms，随后 5/4/3/4ms，连续
hit-fresh。该更改没有把 /api/me 等固定 URL 的其他接口集中到一个 worker。

## 环境与方法

- Docker VM：16 vCPU、约 9.71GiB RAM；NodeBB 12 worker，端口 4567–4578。
- 数据：3000 卡分类、约 30000 主题、4000 私聊房间、60 个压测用户。
- HTTP 经 Caddy :8090，WS 直连 Centrifugo；未覆盖公网 TLS/WS 反代开销。
- 分类 reader 为匿名请求；消息写入使用用户 Bearer token，WS 使用用户 JWT。
  登录用户分类视图按凭证分别缓存，不能从匿名读取成绩直接推断其缓存命中率。
- 每轮先运行 warmup.js；短测 ramp 20 秒、hold 60 秒；完整目标 ramp 120 秒、hold 300 秒。
- 本地 API 配额为 6000，发帖节流放宽；原生私聊通知处于既有禁用状态。
  此结果不能当作生产默认配置的验收；原生通知禁用会影响 Socket.IO 接收、通知铃铛和邮件。
- 续跑为先后顺序测试，数据库、V8 和 OS 缓存没有逐轮清空。因此记录为改动后的实测，
  不将所有差异都归因于单个配置项。修复前后的同 URL 缓存行为另有直接验证。

## 结果

| 轮次 | 在线目标 | 聊天端到端 P95 | 分类读取 P95 | 发送失败率 | 丢弃迭代 |
|---|---:|---:|---:|---:|---:|
| 历史 full8 | 2500 | 29987.55ms | 25467.51ms | 5.784% | 19425 |
| resume-baseline | 500 | 4374.10ms | 1759.14ms | 0.121% | 260 |
| resume-affinity | 500 | 357.45ms | 47.68ms | 0.100% | 0 |
| resume-full（未设堆预算） | 2500 | 9195.00ms | 500.18ms | 0.104% | 3233 |
| resume-budget（256MiB） | 2500 | 1260.50ms | 88.97ms | 0.127% | 113 |
| resume-384（最终本机配置） | 2500 | 133.00ms | 27.13ms | 0.117% | 6 |

最终轮尝试发送 30001 次、成功 29966 次，成功平均约 99.89 msg/s（按 300 秒 hold 计算）；
收到了 18700 个聊天延迟样本。三个脚本门槛均通过，但还不是零错误：发送失败 35 次、
订阅拒绝 5 次、丢弃迭代 6 次，WS transport error 为 0。聊天最大延迟仍达 4272ms。
P95<100ms 的进阶目标尚未达到，P95<500ms 的既定通过线已达到。

最终轮 26 个资源快照中，NodeBB 内存最大为 3.72GiB，swap 始终为 0，
未出现 OOM/worker 重启。负载结束时 3.706GiB，随后业务冒烟完成时为 3.282GiB；
冒烟 20 passed、0 failed。全部 12 个项目容器保持运行，NodeBB/BFF/Mongo healthcheck 正常。

本机 .env 当前保留 `NODEBB_NODE_OPTIONS="--max-old-space-size=384 --max-semi-space-size=8"`。
Compose 中该项是可配置入口，其他环境不设置时沿用 Node 默认行为。

第一次完整续跑虽然比 full8 改善，仍未通过：WS 订阅拒绝 255 次，WS 错误 1 次。
资源日志记录 NodeBB swap 峰值 3075.66MiB，内存/IO pressure 在后半段明显上升。
原先没有 max-memory/NODE_OPTIONS 预算，单进程默认 V8 堆上限为 2240MiB，
12 个 worker 无法在共享 8GiB 容器内按此上限运行。

第二轮通过本地 .env 显式设置 NODEBB_NODE_OPTIONS：old-space 256MiB、
semi-space 8MiB，实测单进程 heap_size_limit=280MiB。Compose 仅新增可配置入口，
未替生产环境强加此数值。重建现有容器后 12 个 /sping 均为 200，再重新预热和完整验证。

256MiB 完整测试共 29902 次发送尝试，29864 次成功；WS 订阅拒绝 19 次。
NodeBB RSS 采样峰值约 3.8GiB，swap 全程为 0，未发生 OOM/worker 重启。
相比无预算时内存问题已经消除，但聊天 P95=1260.5ms 仍未达 500ms；不能宣告通过。
负载结束后业务冒烟再次 20 passed、0 failed。继续以 384MiB 检查更宽堆预算的取舍。

256MiB 负载结束时 NodeBB 为 3.772GiB，随后冒烟完成时为 3.426GiB。
这是一次负载后的回落观察，不能代替长时间泄漏测试。

384MiB 试验的 45 秒稳态诊断窗口（内存最大 worker）：GC 375 次、合计 753ms、
最大单次 23.9ms；事件循环 P99=29.6ms、最大 92.7ms，使用堆约 162MiB。
此窗口没有采到秒级停顿，不能据此认定先前的秒级尾延迟必然由 GC 造成。
缓存刷新期第二个 45 秒窗口：GC 最大 26.1ms、事件循环最大 71.6ms，同样没有秒级停顿。
384MiB 轮包含这两个诊断窗口；没有进行清空 OS/数据库缓存的隔离 A/B 或长时间耐久测试。

短测修复后完成 6000 次发送尝试、5994 次成功；聊天延迟样本为 732 个接收事件，
并非每次发送都有接收样本。每个 WS 随机订阅一个房间，房间成员和消息发送者都来自种子用户。
k6 summary 的 rate 分母包含 ramp 和收尾，不应直接用来判断稳态 100 msg/s 是否达到。

## 验证和诊断

- 现有业务冒烟：20 passed、0 failed。
- 12 个 worker 的 /sping 全部返回 200，缓存 TTL=300000ms 初始化日志共 12 次。
- Caddy validate 通过，配置已热加载并使用官方 formatter 格式化。
- git diff --check、诊断/探针 JS 语法检查和现有 tsc --checkJs 检查通过。
- MongoDB profiler 当前 level=0、slowms=100，未开启全量 profiling。
- 短测采样 worker 堆使用约 197MiB；15 秒 CPU 样本包含大量 idle，主要活跃热点为
  LRU、网络写入、数据库序列化及 Redis pubsub。采样后 inspector 已关闭。
- 预热阶段曾出现内存压力和 swap；未将它误判成 OOM。完整目标资源数据单独保存于
  results/resume-full-resources.jsonl、resume-budget-resources.jsonl、resume-384-resources.jsonl，
  不能凭 OOMKilled=false 推断没有换页。

## 工程收尾

- .gitignore 排除大体积 detail JSON、CPU profile 和含 Bearer token 的 seed-output.json。
- .dockerignore 排除 tools、.git、.tscheck，避免压测产物进入镜像构建上下文。
- send-probe.js 默认改走 Caddy LB；需要隔离单 worker 时显式指定 LT_HTTP_BASE。
- RUNBOOK 修正实际总时长、PowerShell 版本要求、预热与缓存亲和关系，保留复现命令。
- profile-worker.js 提供容器内 CPU 采样，monitor.ps1 记录容器资源与内存压力。

## 尚未覆盖的事项

备份恢复演练、告警规则、私聊 UI/通知完整接入，以及 Read States/Reactions 等后续产品功能
不在本次性能验证范围内。现有分类缓存的失效策略和内部刷新头信任边界仍需单独审查。
写路径每次执行版主权限扫描（user.getModeratedCids 读取全分类）仍是一个后续优化候选，
本轮没有改变其权限语义。原生 web-push 在本地 http canonical URL 下存在 VAPID subject
启动错误，属于既有开发环境问题；本次未将其算作已修复。
